Testing and quality

Logging: levels, release builds and privacy

Use log levels, so you can keep detail in debug builds and send only warnings and errors from release builds. Never log secrets or personal data, because logs can be read by other tools and ends up on servers.

Use it for

Finding bugs during development, and giving yourself useful context when a crash report arrives from a user.

Watch out for

print and debugPrint are only for quick checks. Use a logger package with levels. Never log passwords, tokens, full emails, card numbers or health data. Redact before logging. Keep release logging small, because it costs battery and data.

Example code

// pubspec: logging (or logger)
final log = Logger('Checkout');

void setupLogging() {
  Logger.root.level = kReleaseMode ? Level.WARNING : Level.ALL;
  Logger.root.onRecord.listen((r) {
    if (!kReleaseMode) debugPrint('${r.level.name} ${r.loggerName}: ${r.message}');
    if (r.level >= Level.WARNING) {
      // add a breadcrumb or a non-fatal error to the crash service
      FirebaseCrashlytics.instance.log('${r.loggerName}: ${r.message}');
      if (r.error != null) {
        FirebaseCrashlytics.instance.recordError(r.error, r.stackTrace);
      }
    }
  });
}

// use it
log.fine('cart has ${cart.length} items');          // debug only
log.info('user tapped Buy');
log.warning('API returned 500', error, stack);
log.severe('save failed', error, stack);

// privacy: log ids, not personal data
log.info('signed in user ${user.id}');                // good
// log.info('signed in $email $token');                // never
