FutureBuilder

FutureBuilder watches one Future and rebuilds as its state changes. Your builder reads the snapshot and returns a widget for waiting, for an error and for data.

Use it for

Loading one thing when a screen opens: a profile, a settings record, a single API call.

Watch out for

Create the Future once, in initState or a field. A Future created inside build starts again on every rebuild, which is the classic endless spinner.

The shape of a correct builder
Order of checkspattern-Check connectionState == waiting first, then hasError, then hasData, and only then use data!. Checking hasData first hides errors.
Future created in buildmistake-The classic bug: a new Future on every rebuild means an endless loading spinner. Store it in a field of your State.
Keyboard or theme rebuildsnote-Anything that rebuilds the parent rebuilds this too, which is why the future must be stable.
Alternatives
FutureProvider / AsyncValue (riverpod)package-Caching, retries and one source of truth, which FutureBuilder does not give you.

Example code

late Future<List<User>> _future;

@override
void initState() {
  super.initState();
  _future = api.fetchUsers();   // created once
}

void _reload() => setState(() => _future = api.fetchUsers());

@override
Widget build(BuildContext context) {
  return FutureBuilder<List<User>>(
    future: _future,
    builder: (context, snapshot) {
    if (snapshot.connectionState == ConnectionState.waiting) {
      return const Center(child: CircularProgressIndicator());
    }
    if (snapshot.hasError) {
      return ErrorView(snapshot.error!, onRetry: _reload);
    }
    final users = snapshot.data ?? const [];
    if (users.isEmpty) return const EmptyState();
    return UserList(users);
    },
  );
}
