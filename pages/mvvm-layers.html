State and architecture

App architecture: View, ViewModel, Repository, Service

Flutter's official architecture guide splits an app into a UI layer (Views and ViewModels) and a data layer (Repositories and Services). Data flows up from the services to the screen, and user events flow back down. Each class has one job, so each can be tested alone.

Use it for

Any app that talks to an API or a database, or that will grow past a few screens.

Watch out for

Widgets should hold almost no logic. Repositories should be abstract classes so you can swap in a fake for tests. Add a domain layer only when ViewModels get crowded or repeat logic. For most apps it adds overhead.

Dependency injectionpattern-Pass dependencies in (constructor or Provider) instead of creating them inside classes.

Example code

class HomeViewModel extends ChangeNotifier {
  HomeViewModel({required UserRepository userRepository})
      : _userRepository = userRepository;
  final UserRepository _userRepository;

  UiState<User> state = const Loading();

  Future<void> load() async {
    state = const Loading();
    notifyListeners();
    try {
      state = Data(await _userRepository.getUser());
    } on Exception catch (e) {
      state = Failure(e.toString());
    }
    notifyListeners();
  }
}
