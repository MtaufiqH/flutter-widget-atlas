Clean Architecture in Flutter (and when it is too much)

Clean Architecture splits an app into presentation, domain and data layers, with one rule: dependencies point inward. The domain layer (entities, use cases and repository interfaces) is plain Dart and imports nothing from Flutter or from your data code.

Use it for

Large apps with complex business rules, several data sources, or many developers. It also helps when the business logic must be tested without Flutter.

Watch out for

It adds many files: DTOs, entities, mappers, use cases. A use case that only forwards one call is noise. Flutter's own architecture guide recommends MVVM with UI and data layers, and a domain layer only when logic is complex. Start simple and add layers when you feel the pain.

Example code

lib/
  features/user/
    domain/
      user.dart                 // entity: plain Dart
      user_repository.dart      // abstract class
      get_user.dart             // use case
    data/
      user_dto.dart             // fromJson, toDomain()
      user_repository_impl.dart
    presentation/
      user_page.dart
      user_view_model.dart

// domain/user_repository.dart (no Flutter, no Dio)
abstract class UserRepository {
  Future<User> getUser(int id);
}

// domain/get_user.dart
class GetUser {
  GetUser(this._repo);
  final UserRepository _repo;
  Future<User> call(int id) => _repo.getUser(id);   // add real rules here
}

// data/user_repository_impl.dart
class UserRepositoryImpl implements UserRepository {
  UserRepositoryImpl(this._api);
  final UserApi _api;
  @override
  Future<User> getUser(int id) async => (await _api.getUser(id)).toDomain();
}
